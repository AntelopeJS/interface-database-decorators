A table is a class that extends `Table`. Each field is a property declared with TypeScript's `declare` keyword and the `@Field` decorator. Further decorators add indexes, relations, and initial data.

## The `Table` class

`Table` is the base class of every table definition. It declares `_id: string`, the primary key of every table.

```typescript
import { Table, Field } from "@antelopejs/interface-database-decorators";

class User extends Table {
  @Field("string")
  declare name: string;

  @Field("string")
  declare email: string;
}
```

### Extend with modifiers

The static `Table.with()` method returns a subclass of the table class that holds the mixin methods of the modifiers it receives, such as encryption, hashing, or localization:

```typescript
import {
  Table,
  Field,
  EncryptionModifier,
  Encrypted,
} from "@antelopejs/interface-database-decorators";

const secretKey = process.env.ENCRYPTION_KEY;
if (!secretKey || Buffer.byteLength(secretKey, "utf8") !== 32) {
  throw new Error("ENCRYPTION_KEY must contain exactly 32 UTF-8 bytes");
}

class SensitiveData extends Table.with(EncryptionModifier) {
  @Field("string")
  declare publicContent: string;

  @Encrypted({ secretKey })
  @Field("string")
  declare secureContent: string;
}
```

Provide a high-entropy key through your secret manager, and never a default key. See [Table modifiers](./3.table-modifiers.md#encryptionmodifier) for the key format and the date precision limit.

## The `Index` decorator

The `Index` decorator marks a field as a database index. An indexed field serves lookups through `getAll()` and `between()` on the AQL table, and through the model's `getBy()`. `@Index` on a symbol-keyed property throws, because a database index names a field.

```typescript
import { Table, Field, Index } from "@antelopejs/interface-database-decorators";

class User extends Table {
  @Index()
  @Field("string")
  declare email: string;

  @Field("string")
  declare name: string;
}
```

### Options

| Option          | Type      | Description                                                         |
| --------------- | --------- | ------------------------------------------------------------------- |
| `group`         | `string`  | Assign the field to a named compound index group.                   |
| `crossInstance` | `boolean` | Also keep the index fast for queries that run across all instances. |
| `unique`        | `boolean` | Refuse two rows of the instance with the same key.                  |

### Cross-instance indexes

Every index is scoped to the schema instance. Set `crossInstance: true` when queries across all instances (on the `CROSS_INSTANCE` instance) also use the index. The database driver then maintains an additional index for those queries.

The option never changes query results. Without it, a cross-instance query that names the index returns the same rows but runs slower, and the `@antelopejs/mongodb` and `@antelopejs/rethinkdb` drivers log a warning once per index. Leave it unset for an index that only queries within one instance use, because each extra index costs storage and write time.

```typescript
import { Field, Index, Table } from "@antelopejs/interface-database-decorators";

class User extends Table {
  @Index({ crossInstance: true })
  @Field("string")
  declare email: string;
}
```

For a compound index, setting `crossInstance: true` on any field of the group applies it to the whole group.

### Unique indexes

Set `unique: true` to refuse a second row with the same key in one instance. The write that would store it throws `DuplicateKeyError` from `@antelopejs/interface-database`, which names the index and its fields. Test for it with `IsDuplicateKeyError`. Rows of different instances may share a key.

```typescript
import { Field, Index, Table } from "@antelopejs/interface-database-decorators";

class Template extends Table {
  @Index({ unique: true })
  @Field("string")
  declare slug: string;
}
```

For a compound index, setting `unique: true` on any field of the group makes the whole group's key unique. Not every database module can enforce a unique secondary index. A module that cannot, such as `@antelopejs/rethinkdb`, refuses the schema instead of ignoring the option.

### Compound indexes

Assign multiple fields to the same index group to create a compound index:

```typescript
import {
  Table,
  Field,
  Index,
  Relation,
} from "@antelopejs/interface-database-decorators";

class User extends Table {
  @Field("string")
  declare name: string;
}

class UserActivity extends Table {
  @Index({ group: "user_action" })
  @Field("string")
  @Relation({ to: () => User })
  declare userId: string;

  @Index({ group: "user_action" })
  @Field("string")
  declare action: string;

  @Field("date")
  declare timestamp: Date;
}
```

## The `Field` decorator

`@Field(type)` declares the type of a property. The type goes unchanged into the `TableDefinition.fields` map that the database module receives. It accepts every member of the `FieldType` union, for example a string token such as `"string"` or `"number"`, an array, a nested record, or an io-ts codec.

```typescript fragment
import * as t from "io-ts";
import {
  Table,
  Field,
  Index,
  RegisterTable,
} from "@antelopejs/interface-database-decorators";

@RegisterTable("orders", "shop")
class Order extends Table {
  @Field("string")
  declare id: string;

  @Field(t.union([t.literal("open"), t.literal("closed")]))
  declare status: "open" | "closed";

  @Index()
  @Field("number")
  declare total: number;
}
```

Properties without `@Field` are left out of `fields`. `@Field` and `@Index` each write their own metadata, so they combine in either order.

## The `Relation` decorator

The `Relation` decorator declares a link from a field to another table. It is metadata only. Database modules do not enforce it, with no foreign key constraint and no check that the target exists. Introspection tools read it to show the links between tables, for example in a schema diagram or to navigate to related records.

```typescript fragment
import {
  Table,
  Field,
  Index,
  Relation,
} from "@antelopejs/interface-database-decorators";

class Comment extends Table {
  @Index()
  @Field("string")
  @Relation({ to: () => Post })
  declare postId: string;

  @Field(["string"])
  @Relation({ to: () => Tag, many: true })
  declare tagIds: string[];
}
```

### Options

| Option    | Type                 | Description                                                                      |
| --------- | -------------------- | -------------------------------------------------------------------------------- |
| `to`      | `() => typeof Table` | Thunk returning the target table class (lazy to allow forward references).       |
| `toField` | `string`             | Target field name. Defaults to the target table's primary key.                   |
| `many`    | `boolean`            | The decorated field holds multiple target keys (many targets per source record). |

`@Relation` writes its own metadata, so it combines with `@Field` and `@Index` in any order.

## The `RegisterTable` decorator

The `RegisterTable` class decorator gives a table class its table name and its schema. `RegisterSchema` builds the schema definition from these registrations.

```typescript
import {
  Table,
  Field,
  Index,
  RegisterTable,
} from "@antelopejs/interface-database-decorators";

@RegisterTable("users", "myapp")
class User extends Table {
  @Index()
  @Field("string")
  declare email: string;

  @Field("string")
  declare name: string;
}
```

The first argument is the table name in the database, and the second is the schema name.

## The `Fixture` decorator

The `Fixture` decorator defines the rows to insert into an empty table. It receives a generator function that returns them.

```typescript
import {
  Table,
  Field,
  Fixture,
} from "@antelopejs/interface-database-decorators";

@Fixture(() => [
  { _id: "admin", name: "Administrator" },
  { _id: "user", name: "Standard User" },
  { _id: "guest", name: "Guest" },
])
class UserRole extends Table {
  @Field("string")
  declare name: string;
}
```

The generator function:

- Receives the table class registered into the schema, which is the decorated class or a subclass of it.
- Can return a single object, an array of objects, or a `Promise` of either.
- Runs when `RegisterSchema` finds the table empty, so a later start inserts nothing again.

Only a table registered with `@RegisterTable` gets its fixture, from `RegisterSchema`. Each row goes through the same conversion as a model insert, so modifiers and the `insert` event apply. A row without an `_id` gets `<table>:fixture:<position>`, so two processes that start on the same empty table write one row between them.

### Async generators

```typescript fragment
import {
  Field,
  Fixture,
  Table,
} from "@antelopejs/interface-database-decorators";

@Fixture(async () => {
  const defaults = await loadDefaultConfig();
  return defaults.map((cfg) => ({
    _id: cfg.key,
    value: cfg.value,
  }));
})
class SystemConfig extends Table {
  @Field("string")
  declare value: string;
}
```

## Inheritance

A table class can extend another table class. The subclass starts with a copy of its parent's table and schema names, fields, indexes, and fixture, so decorators on the subclass do not change the parent:

```typescript
import {
  Table,
  Field,
  Index,
  Relation,
} from "@antelopejs/interface-database-decorators";

class BaseEntity extends Table {
  @Field("date")
  declare createdAt: Date;

  @Field("date")
  declare updatedAt: Date;
}

class User extends BaseEntity {
  @Index()
  @Field("string")
  declare email: string;

  @Field("string")
  declare firstName: string;

  @Field("string")
  declare lastName: string;
}

class Post extends BaseEntity {
  @Index()
  @Field("string")
  @Relation({ to: () => User })
  declare authorId: string;

  @Field("string")
  declare title: string;

  @Field("string")
  declare content: string;
}
```

## Register a schema

The `RegisterSchema` function builds a `SchemaDefinition` from every table that `@RegisterTable` registered for the schema ID. It constructs the `Schema`, which the database module provisions, and binds each table class to it (see [Open a table from its class](#open-a-table-from-its-class)). Then it inserts the fixtures of the tables that are empty.

Call it in the module that declares the tables. The binding then follows that module's database, whichever module later uses the classes.

```typescript
import { RegisterSchema } from "@antelopejs/interface-database-decorators";

await RegisterSchema("myapp");
```

### Parameters

| Parameter  | Type     | Description                                                        |
| ---------- | -------- | ------------------------------------------------------------------ |
| `schemaId` | `string` | Schema id matching the `@RegisterTable(_, schemaId)` declarations. |

`RegisterSchema` returns `Promise<void>`. It throws `No tables registered for schema '<schemaId>'` when no class registers into the schema.

## Open a table from its class

`Table.table()` returns the AQL table a class describes, in the schema `RegisterSchema` bound it to:

```typescript fragment
import {
  RegisterSchema,
  RegisterTable,
  Table,
} from "@antelopejs/interface-database-decorators";

@RegisterTable("users", "myapp")
class User extends Table {
  declare name: string;
}

await RegisterSchema("myapp");

User.table(); // default instance of "myapp"
User.table("tenant-1"); // instance "tenant-1" (CROSS_INSTANCE is accepted too)
User.table(db); // db.table("users") on a SchemaInstance you already hold
```

Given a `SchemaInstance`, `table()` takes the table from it as is, so pass an instance of the class's own schema. A class without `@RegisterTable` throws `<Class> has no table name`. A class that no `RegisterSchema` call bound, and whose schema name has no schema, throws `<Class> is not bound to a schema`.
